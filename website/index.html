Async?

About the project

A speedup is notevidence forasynchrony.

Block-asynchronous iterative methods relax global synchronization, trading cheaper iterations for extra iterations caused by stale data. I examined this trade-off for a five-point Jacobi solver of an implicit diffusion step on a single consumer GPU, an NVIDIA GeForce RTX 5050 Laptop GPU, on grids from 512² to 18432².

The block-asynchronous kernel does two things at once: it tolerates stale data, and it reads each grid point from memory only once per D sweeps. The second effect is temporal locality, which an exact, fully synchronous method can also exploit. This project separates the two.

The problem01 / 07

One implicit diffusion step,a five-point stencil.

Jacobi update with uⁿ held fixed

u(k+1) = uⁿ + r·Σu(k) + Δt·f1 + 4r
r = αΔt / h² · Σu = N + S + E + W

The transient equation ∂u/∂t = α∇²u + f is discretized on an N×N unit square. Each backward-Euler step solves a linear system; Jacobi sweeps it to convergence. The top boundary is held at 100, the others at 0, and the source is either a point at the centre or a Gaussian with σ = N/16. Each run solves ten consecutive time steps in float32.

The iteration matrix has spectral radius below 4r/(1+4r), so the number of sweeps grows with r but not with N: about 35, 226 and 1417 sweeps per step for r = 1, 10 and 100.

A step converges when the relative true residual ρ = ‖b − Au‖∞ / ‖b‖∞ drops below 10⁻⁵, checked every M = 8 sweeps. Because A is strictly diagonally dominant, the residual directly bounds the solution error. It is computed in a difference form that avoids float32 cancellation, which the naive form underestimated by about 2.5× at r = 100.

RQ1

Can relaxing global synchronization reduce time to convergence despite the extra iterations it causes, and under which conditions?

RQ2

Can the best synchronization strategy be predicted from features known before execution?

A mistake worth sharing. The first solver used the current iterate in place of uⁿ. It still converged, but to the steady-state Poisson problem, needing 3.7×10⁵ sweeps at N = 512 and 1.25×10⁶ at N = 1024, a count that grows as O(N²). Fixing it changed iteration counts by three orders of magnitude and made r a meaningful parameter.

Synchronous

Wait for everyone

Each sweep is its own kernel launch. No block may start sweep k+1 until every block has finished sweep k.

  • Fresh data, fewest iterations
  • A global barrier every sweep

Block-asynchronous

Keep sweeping locally

A block sweeps its tile D times in shared memory, using frozen halo values from its neighbours, before anyone exchanges data.

  • Far fewer global synchronizations
  • Stale neighbour values mean extra sweeps

S = Tsync / Tx = 1 / (c · s) — c: cost per sweep · s: sweep ratio

Method · 02 / 07

Four ways
to sweep a grid.

All kernels share one arithmetic definition and are validated bit for bit against a NumPy reference, down to identical sweep counts.

01sync

Synchronous baseline

One thread per point in 32×8 blocks, ping-pong buffers. A reduction kernel computes both residual norms every M sweeps with warp shuffles and copies them to the host, which decides whether to continue.

Strengthened later with a fused right-hand side (uⁿ + Δt·f computed once per step), cutting traffic from 16 to 12 bytes per point per sweep.

02D1 – D8

Block-asynchronous

After Anzt et al.: each block loads its tile plus a one-cell halo into shared memory and sweeps it D ∈ {1, 2, 4, 8} times with __syncthreads() between sweeps. Values read across a tile edge can be up to D−1 sweeps old.

With D = 1 it reproduces the synchronous iterates exactly.

03G-asc · G-desc · G-fb

Residual-guided

D is just a kernel argument, so it can change between launches for free. G-asc and G-desc step D up or down as ρ crosses 10⁻², 10⁻³, 10⁻⁴ (latched, to stop oscillation).

G-fb is a hill-climbing controller: start at D = 1, measure −ln(ρₖ/ρₖ₋₁) per ms, double D while the rate holds, halve it on a >10% drop. A settling window skips the residual bump right after each change.

04T2 – T8

Exact temporal blocking

The ghost-zone technique of Meng & Skadron. Each block loads a halo D cells wide; in sweep s it updates only points at least s+1 cells from the edge. After D sweeps the tile holds exactly what D synchronous sweeps would produce.

Same data reuse as block-async, zero staleness. It pays with redundant work: a Tx×Ty tile loads (Tx+2D)(Ty+2D) points.

The barrier isn't the bottleneck. The host round trip is.

Kernel launches are queued asynchronously, and global sweeps are served largely from L2: the fused sync kernel sustains 580–640 GB/s at N = 1024, well above the 384 GB/s DRAM peak, consistent with a 12–16 MiB working set in the 32 MiB L2.

The block-async kernel also carries a fixed cost per launch: at N = 512, a D1 launch took ≈ 9.4 µs and a D8 launch ≈ 19.4 µs against ≈ 4.4 µs for a sync sweep. Each extra in-tile sweep costs ≈ 1.4 µs, but loading and storing the tile costs about two synchronous sweeps.

The synchronization that costs time, the host round trip that decides convergence, is something inter-block asynchrony can't remove.

Results · beyond L205 / 07

Past 32 MiB,the picture flips.

Once the grid outgrows L2, the synchronous kernel becomes bandwidth-bound. Kernels that sweep several times per pass through device memory now have a real advantage, and both temporal blocking and block-asynchronous relaxation overtake the synchronous kernel.

The speedups did not keep growing with N. From 2048² to 18432² the working set grows 81×, yet speedups stay inside a flat band. Beyond L2 there is no further cache level to fall out of.

The two factors of S = 1/(c·s) explain why: s is fixed by the numerics (D8@32×16 needs exactly 1.738× the sync sweeps at r = 10 for every N from 1024 to 16384), and c is fixed by the memory regime (0.39–0.42 for D8, 0.71–0.76 for T4).

How optimistic was the first result?

1.76× shrankto 1.02–1.13×.

The first out-of-cache measurement looked like a clear win for asynchrony. It didn't survive a fair comparison, and how it shrank is one of the main findings.

Takeaway. When an asynchronous kernel also changes the memory access pattern, the comparison needs a synchronous baseline that changes it the same way. Fusing the right-hand side alone removed ≈ 15% of the apparent advantage; most of what remained came from temporal locality, not stale data.

Adaptive & learned selection06 / 07

Cache fit and rdecide the winner.

G-fb came within 10% of the best static strategy per configuration without being told N or r, and beat every static strategy in one configuration. At r = 100 it changed D between 186 and 212 times per run, each change reacting to the residual disturbance of the previous one.

Out of cache it was 1.17–1.54× faster than the unfused sync kernel at N = 2048 and 4096, within 10–15% of the best static choice. In cache it lost (0.69–0.84×) because its search pushes towards larger D, which doesn't pay there. A version that can fall back to synchronous behaviour would recover much of that.

Depth-2 decision tree, 16 configs

Split values are midpoints between measured points. The data establish only that the switch lies between N = 1024 (ratio 0.5) and 2048 (ratio 2.0), an interval containing the physical L2 capacity, and between r = 1 and 10.

On the main matrix, a tree on (N, source, r) picked the fastest static strategy every time, but only two configurations had a non-sync label, so a second selector was trained on the 16-config extension dataset: classes sync (3), temporal blocking (5) and block-async (8).

Conclusion07 / 07

The L2 cachegoverns the answer.

  1. RQ1 · In cache, don't relax

    While the working set fits in L2, plain synchronous Jacobi is fastest. Barriers between blocks are cheap; the costly synchronization is the host round trip for convergence checks, which inter-block asynchrony can't touch.

  2. Out of cache, locality does most of the work

    Sweeping several times per pass through memory gives a step change of ≈ 1.3–1.5× that stays flat up to the largest grid that fits in memory. About 1.3× is available to an exact method with no staleness.

  3. Asynchrony adds ≈ 10%, and only sometimes

    Relaxing synchronization adds 10–13% over temporal blocking when time steps need many iterations (r ≥ 10), because a one-cell halo is cheaper than redundant halo work. When steps are short (r = 1) it is 16–19% slower.

  4. RQ2 · Two features predict the winner

    Working set relative to L2, and r. A depth-2 tree recovers this rule and cuts the best fixed strategy's mean slowdown by almost two-thirds (13.6% → 4.9%), but cannot extrapolate across the cache boundary.

Practical advice

  • Measure the cost of convergence checks before trying to remove barriers. Checking on the device and reporting to the host less often may save more than changing the iteration.
  • Compare asynchronous kernels against a baseline whose memory traffic is already minimized.
  • Compute a block-async sweep ratio on the CPU at small N: it doesn't depend on N, and with one GPU per-sweep cost it predicts the speedup at larger sizes.

Threats to validity

  • One laptop GPU; a larger L2 or different bandwidth/compute ratio moves the regime boundary.
  • The temporal-blocking kernel is far simpler than AN5D or EBISU; the 10–13% margin is fragile.
  • Not a fully asynchronous persistent kernel; cache residency inferred without counters; 3–5 repeats; small selector datasets.

What's next

  • Device-side convergence detection.
  • State-of-the-art temporal blocking and persistent kernels (EBISU, PERKS).
  • Fully asynchronous variants.
  • Other GPUs, so a selector can learn across cache sizes rather than within one.
